# RAG 介绍与完整功能组件说明

## 一、什么是 RAG？

RAG 是 **Retrieval-Augmented Generation**，中文通常叫 **检索增强生成**。

简单说：

> RAG = 先从知识库里查资料，再把查到的资料交给大模型，让大模型基于资料回答问题。

它解决的是大模型本身“记不住私有知识、知识可能过期、容易编造答案”的问题。

---

## 二、为什么需要 RAG？

大模型本身有几个典型限制。

### 1. 知识不是实时的

模型训练完成后，它的知识就固定了。比如公司上周刚更新的产品文档，模型本身不知道。

### 2. 不知道私有数据

例如：

- 公司内部文档
- 项目代码说明
- 客服知识库
- 合同条款
- 产品手册
- 数据库里的业务资料

这些内容没有进入模型训练数据，模型不能直接回答。

### 3. 容易幻觉

如果用户问一个模型不知道的问题，模型可能会“编”一个看起来很合理但实际错误的答案。

### 4. 微调成本高

可以通过微调让模型学习新知识，但微调通常：

- 成本高
- 更新慢
- 不适合频繁变化的知识
- 更适合学习“风格、格式、能力”，不适合当知识库用

所以 RAG 的核心思想是：

> 不把所有知识塞进模型参数里，而是在回答前动态检索相关资料。

---

## 三、RAG 的基本流程

一个典型 RAG 流程分为两个阶段：

1. 知识入库阶段
2. 用户问答阶段

---

## 四、知识入库阶段

假设有一份 PDF、Word、Markdown、网页、数据库记录或者代码文档，RAG 系统通常会这样处理。

### 1. 文档加载

把原始资料读取进系统。

来源可以是：

- PDF
- Word
- Markdown
- HTML
- TXT
- 数据库
- Notion / Confluence
- Git 仓库
- API 返回内容

### 2. 文本清洗

去掉无用内容，例如：

- 页眉页脚
- 多余空格
- HTML 标签
- 广告内容
- 重复段落
- 无意义符号

### 3. 文档切块

大模型和向量数据库都不适合直接处理超长文档，所以要把文档切成小块。

例如一篇 10 万字的产品手册，可以切成：

```text
chunk 1: 第 1-500 字
chunk 2: 第 450-950 字
chunk 3: 第 900-1400 字
...
```

通常会有一定重叠，比如每块 500 字，相邻块重叠 50 字。

重叠的目的是避免答案刚好跨越两个片段时丢失上下文。

### 4. Embedding 向量化

每个文本块会通过 Embedding 模型转换成一个向量。

例如：

```text
"如何重置密码？"
```

会被转换成类似：

```text
[0.012, -0.238, 0.991, ...]
```

这个向量表示这段文本的“语义”。语义相近的文本，在向量空间里距离更近。

例如：

```text
"如何重置密码？"
"忘记密码怎么办？"
"怎么找回账号密码？"
```

这几句话字面不同，但语义接近，向量也会接近。

### 5. 存入向量数据库

每个 chunk 通常会存储：

```json
{
  "id": 123,
  "documentId": 10,
  "content": "如果用户忘记密码，可以点击登录页的忘记密码按钮...",
  "embedding": [0.012, -0.238, 0.991],
  "metadata": {
    "source": "用户手册.pdf",
    "page": 12,
    "section": "账号管理"
  }
}
```

常见向量数据库包括：

- pgvector
- Milvus
- Weaviate
- Pinecone
- Qdrant
- Elasticsearch vector search

Hify 项目规划使用 **pgvector**。

## 五、用户问答阶段

当用户提问时，RAG 系统会执行以下流程。

### 1. 用户提问

```text
用户：忘记密码后怎么重置？
```

### 2. 问题向量化

系统会把用户问题也转成向量：

```text
"忘记密码后怎么重置？" -> [0.025, -0.191, 0.876, ...]
```

### 3. 向量检索

拿这个问题向量去向量数据库里查相似 chunk。

比如查到：

```text
chunk A: 用户忘记密码时，可以点击登录页的“忘记密码”按钮...
chunk B: 密码重置链接有效期为 30 分钟...
chunk C: 如果邮箱不可用，需要联系管理员重置...
```

### 4. 组装 Prompt

系统把检索到的资料和用户问题一起发给大模型。

例如：

```text
你是一个客服助手。请只根据下面的资料回答用户问题。

资料：
1. 用户忘记密码时，可以点击登录页的“忘记密码”按钮。
2. 系统会发送密码重置链接到用户邮箱。
3. 密码重置链接有效期为 30 分钟。
4. 如果邮箱不可用，需要联系管理员处理。

用户问题：
忘记密码后怎么重置？

请给出简洁回答。
```

### 5. 大模型生成答案

```text
如果你忘记密码，可以在登录页点击“忘记密码”，系统会向你的邮箱发送密码重置链接。该链接有效期为 30 分钟。如果你的邮箱无法使用，请联系管理员处理。
```

这就是 RAG。

## 六、RAG 和普通大模型问答的区别

普通问答：

```text
用户问题 -> 大模型 -> 答案
```

RAG 问答：

```text
用户问题 -> 检索知识库 -> 找到相关资料 -> 大模型基于资料生成答案
```

核心区别是：

> 普通问答依赖模型已有知识，RAG 依赖外部知识库。

---

## 七、RAG 的关键技术点

### 1. Chunk 切分策略

切得太大：

- 检索不精准
- Prompt 太长
- 成本高

切得太小：

- 上下文不足
- 答案缺信息
- 容易断章取义

常见经验：

```text
普通知识库：300-800 中文字一块
技术文档：500-1200 中文字一块
代码文档：按函数、类、模块切
法律合同：按条款切
```

### 2. Top-K 检索

Top-K 表示取最相关的前 K 条资料。

例如：

```text
topK = 5
```

就是取最相关的 5 个 chunk。

K 太小可能漏信息，K 太大可能引入噪声。

### 3. 相似度阈值

如果检索结果相似度太低，就不应该硬答。

例如：

```text
相似度 < 0.5：认为知识库没有相关内容
```

这时可以回答：

```text
当前知识库中没有找到相关信息。
```

### 4. Hybrid Search 混合检索

纯向量检索擅长语义匹配，但有时候不擅长精确关键词。

例如：

```text
错误码 HIFY-4032 是什么？
```

这种问题里关键词非常重要，纯向量检索可能不如关键词搜索。

所以常见做法是：

```text
向量检索 + 关键词检索
```

然后合并结果。

### 5. Rerank 重排序

第一轮检索可能找出 20 条候选资料，然后用 reranker 模型重新排序，选出最相关的 3-5 条。

流程：

```text
用户问题 -> 初步检索 top 20 -> rerank -> 取 top 5 -> 生成答案
```

Rerank 能显著提升 RAG 质量，但会增加延迟和成本。

### 6. Metadata 过滤

文档 chunk 通常带有 metadata。

例如：

```json
{
  "department": "HR",
  "documentType": "policy",
  "createdAt": "2026-05-01"
}
```

用户问：

```text
研发部门的报销规则是什么？
```

可以先过滤：

```text
department = "研发"
documentType = "policy"
```

再做向量检索。

### 7. 引用与溯源

RAG 很重要的一点是答案可追溯。

不仅要回答，还要告诉用户：

- 来自哪个文档
- 哪个章节
- 哪一页
- 哪个片段

这对企业内部系统尤其重要。

---

## 八、RAG 的优点

### 1. 可以接入私有知识

企业内部文档、项目资料、数据库内容都可以接入。

### 2. 知识更新方便

文档变了，只需要重新索引相关文档，不需要重新训练模型。

### 3. 降低幻觉

模型被要求基于检索到的资料回答，可以减少乱编。

### 4. 可溯源

可以展示引用来源，提高可信度。

### 5. 成本相对可控

相比微调，RAG 更适合频繁变化的知识场景。

---

## 九、RAG 的缺点

### 1. 检索不到就答不好

RAG 的答案质量高度依赖检索质量。

如果相关资料没被检索出来，大模型就无法正确回答。

### 2. 文档切分很关键

切分不好会导致：

- 语义不完整
- 检索片段不准确
- 答案缺上下文

### 3. 会引入额外复杂度

需要维护：

- 文档解析
- Embedding
- 向量数据库
- 检索策略
- 重排序
- 引用管理

### 4. 不适合复杂推理全部外包

RAG 适合“基于资料回答”，但如果问题需要复杂计算、工作流执行、数据库实时查询，可能还需要工具调用或 Agent。

---

## 十、RAG 和微调的区别

| 对比项 | RAG | 微调 |
|---|---|---|
| 目的 | 接入外部知识 | 改变模型行为、风格、能力 |
| 更新知识 | 快，重新索引即可 | 慢，需要重新训练 |
| 成本 | 较低 | 较高 |
| 私有知识问答 | 很适合 | 不一定适合 |
| 可溯源 | 容易做引用 | 不容易 |
| 幻觉控制 | 较好 | 仍可能幻觉 |
| 适合场景 | 企业知识库、文档问答、客服 | 固定格式输出、领域风格、特定任务能力 |

一句话：

> RAG 适合让模型“查资料”，微调适合让模型“学会某种做事方式”。

## 十一、一个实际例子

假设要在 Hify 里做一个“公司制度问答 Agent”。

### 知识库内容

上传：

```text
员工手册.pdf
报销制度.docx
请假流程.md
信息安全规范.pdf
```

### 入库流程

```text
文档上传
-> 文本解析
-> 文本切块
-> Embedding 向量化
-> 存入 pgvector
```

### 问答流程

用户问：

```text
我出差打车能报销吗？
```

系统：

```text
问题向量化
-> 从 pgvector 检索报销制度相关片段
-> 找到“市内交通费报销规则”
-> 组装 Prompt
-> LLM 回答
```

最终回答：

```text
根据《报销制度》，出差期间因公务产生的打车费用可以报销，但需要提供发票，并在报销单中注明出发地、目的地和事由。

参考来源：
- 报销制度.docx，第 3 章：交通费报销
```

# 完整 RAG 功能需要哪些组件？

实现一个完整的 RAG 功能，通常可以拆成四大链路：

1. 知识入库链路
2. 检索链路
3. 生成链路
4. 管理与评估链路

整体流程如下：

```text
文档上传
  ↓
文档解析
  ↓
文本清洗
  ↓
文档切块
  ↓
Embedding 向量化
  ↓
向量存储 / 索引
  ↓
用户提问
  ↓
问题改写 / 意图识别
  ↓
检索器 Retriever
  ↓
重排序 Reranker
  ↓
上下文组装
  ↓
LLM 生成回答
  ↓
引用来源 / 结果返回
```

---

## 1. 知识库管理组件

### 功能

负责管理“哪些知识可以被 RAG 使用”。

通常包括：

- 创建知识库
- 修改知识库名称、描述
- 删除知识库
- 查看知识库下的文档
- 配置知识库检索参数
- 将知识库绑定到 Agent

### 典型数据

```text
knowledge_base
- id
- name
- description
- embedding_model
- retrieval_top_k
- similarity_threshold
- created_at
- updated_at
```

### 作用

知识库是 RAG 的逻辑容器。

例如：

```text
知识库 A：公司制度
知识库 B：产品文档
知识库 C：技术手册
```

不同 Agent 可以绑定不同知识库。

---

## 2. 文档管理组件

### 功能

负责文档生命周期管理。

包括：

- 上传文档
- 删除文档
- 查看文档解析状态
- 重新解析文档
- 重新向量化文档
- 文档版本管理
- 文档状态管理

### 常见文档状态

```text
UPLOADED      已上传
PARSING       解析中
PARSED        解析完成
CHUNKING      切块中
EMBEDDING     向量化中
INDEXED       已索引
FAILED        处理失败
```

### 典型数据

```text
document
- id
- knowledge_base_id
- name
- file_type
- file_size
- storage_path
- status
- error_message
- created_at
- updated_at
```

### 作用

文档管理负责把原始文件纳入 RAG 系统，但本身不负责理解内容。

---

## 3. 文件存储组件

### 功能

保存用户上传的原始文件。

可以使用：

- 本地磁盘
- MinIO
- S3
- OSS
- 数据库存储，不推荐大文件直接进数据库

### 存储内容

```text
原始 PDF
Word 文件
Markdown 文件
TXT 文件
HTML 文件
CSV 文件
```

### 作用

原始文件需要保留，原因是：

- 方便重新解析
- 方便重新切块
- 方便重新向量化
- 方便用户下载原文
- 方便引用来源追溯

---

## 4. 文档解析组件

### 功能

把不同格式的文件转换成纯文本或结构化文本。

例如：

```text
PDF -> text
DOCX -> text
HTML -> markdown/text
Markdown -> text
CSV -> structured text
```

### 常见解析能力

| 文件类型 | 解析方式 |
|---|---|
| TXT | 直接读取 |
| Markdown | 保留标题结构 |
| PDF | 提取页面文本 |
| DOCX | 提取段落、标题、表格 |
| HTML | 去标签、提正文 |
| CSV/Excel | 转换为文本表格 |

### 输出内容

```json
{
  "text": "文档正文内容...",
  "metadata": {
    "fileName": "员工手册.pdf",
    "pageCount": 20,
    "author": "HR"
  }
}
```

### 作用

文档解析质量直接影响后续检索质量。

如果解析出来的文本混乱，比如顺序错乱、表格丢失、页眉页脚干扰严重，RAG 效果会很差。

---

## 5. 文本清洗组件

### 功能

对解析出的文本做清理。

常见清洗内容：

- 去除多余空行
- 去除重复页眉页脚
- 去除乱码
- 去除无意义符号
- 合并断行
- 规范空格
- 保留标题层级
- 修复 PDF 解析导致的换行问题

### 示例

清洗前：

```text
Hify 产品手册

第 12 页

用 户 可 以 通 过
控 制 台 创 建 Agent。
```

清洗后：

```text
用户可以通过控制台创建 Agent。
```

### 作用

清洗的目标不是“美化文本”，而是让文本更适合切块和检索。

---

## 6. 文档切块组件

### 功能

把长文档切成多个小片段 chunk。

原因是：

- 大模型上下文有限
- 向量检索不能直接处理超长文档
- 片段越精确，检索越准确

### 常见切块方式

#### 固定长度切块

例如每 500 字一个 chunk。

优点：实现简单、稳定可控。

缺点：可能切断语义。

#### 按段落切块

根据换行、段落切分。

优点：语义更自然。

缺点：长短不均。

#### 按标题层级切块

适合 Markdown、技术文档、产品文档。

例如：

```text
# 账号管理
## 修改密码
## 找回密码
```

可以按标题结构切。

优点：保留章节语义，引用更清晰。

缺点：对文档结构要求较高。

#### 递归切块

先按标题切，再按段落切，再按句子切，最后按长度兜底。

这是比较常见的高级方案。

### Chunk 典型结构

```text
document_chunk
- id
- document_id
- knowledge_base_id
- content
- chunk_index
- token_count
- page_number
- section_title
- metadata
- embedding_id/vector
- created_at
```

### 关键参数

```text
chunkSize: 每块大小
chunkOverlap: 块之间重叠大小
separator: 切分符
maxChunkSize: 最大长度
minChunkSize: 最小长度
```

### 作用

切块是 RAG 质量的核心环节之一。

切得太大，检索不准；切得太小，答案缺上下文。

---

## 7. Embedding 向量化组件

### 功能

把文本转换成向量。

例如：

```text
"如何创建 Agent？"
```

转换成：

```text
[0.021, -0.114, 0.883, ...]
```

向量表达文本的语义。语义相近的文本，向量距离更近。

### 向量化对象

通常包括：

- 文档 chunk
- 用户问题

### 常见 Embedding 模型

- OpenAI embedding
- BGE
- E5
- Jina Embeddings
- 通义、智谱、百度等 embedding 模型
- 本地 embedding 模型

### 组件职责

- 调用 embedding 模型
- 控制超时
- 批量向量化
- 处理失败重试
- 记录向量维度
- 保证同一个知识库使用兼容的 embedding 模型

### 作用

Embedding 决定了“语义相似”的基础能力。

如果 embedding 模型不好，后续检索再优化也有限。

---

## 8. 向量数据库 / 向量索引组件

### 功能

存储 chunk 的向量，并支持相似度检索。

常见向量数据库：

- pgvector
- Milvus
- Qdrant
- Weaviate
- Pinecone
- Elasticsearch vector search

Hify 项目技术栈里规划的是 **pgvector**。

### 存储内容

```text
chunk_id
knowledge_base_id
document_id
content
embedding vector
metadata
```

### 常见检索方式

#### 余弦相似度

```text
cosine similarity
```

适合大多数文本语义检索。

#### 欧氏距离

```text
L2 distance
```

#### 内积

```text
inner product
```

具体用哪种取决于 embedding 模型。

### 作用

向量库是 RAG 的检索基础设施。

它负责根据用户问题找到语义最接近的文档片段。

---

## 9. 关键词检索组件

### 功能

基于关键词、倒排索引、全文搜索查找相关内容。

可以使用：

- MySQL fulltext
- PostgreSQL full text search
- Elasticsearch
- OpenSearch
- Lucene

### 为什么需要关键词检索？

纯向量检索对语义相似很强，但对精确匹配不一定稳定。

例如：

```text
错误码 HIFY-4032 是什么意思？
接口 /api/v1/providers/{id}/test-connection 怎么用？
配置项 llm.timeout 的默认值是多少？
```

这些问题里，关键词非常重要。

### 作用

关键词检索通常和向量检索结合，形成 Hybrid Search。

---

## 10. 混合检索组件 Hybrid Search

### 功能

同时使用：

```text
向量检索 + 关键词检索
```

然后合并结果。

### 示例流程

```text
用户问题
  ↓
向量检索 top 20
关键词检索 top 20
  ↓
结果合并
  ↓
去重
  ↓
打分融合
  ↓
得到候选 chunk
```

### 常见融合方式

#### 加权得分

```text
final_score = vector_score * 0.7 + keyword_score * 0.3
```

#### RRF

RRF 即 Reciprocal Rank Fusion，按排名融合结果。

```text
score = 1 / (k + rank)
```

### 作用

混合检索能同时兼顾：

- 语义相似
- 精确关键词
- 专有名词
- 错误码
- API 名称
- 配置项名称

---

## 11. Query 预处理组件

### 功能

在检索前处理用户问题。

常见能力包括：

#### 问题清洗

去掉无意义符号、空格、噪声。

#### 问题改写

把口语化问题改成更适合检索的问题。

例如：

```text
用户：这个怎么配？
```

结合上下文改写为：

```text
如何配置 Hify 的模型提供商？
```

#### 多轮对话补全

用户可能问：

```text
用户：怎么创建 Agent？
助手：...
用户：那怎么绑定知识库？
```

第二个问题需要补全为：

```text
Agent 怎么绑定知识库？
```

#### 查询扩展

把一个问题扩展成多个查询。

例如：

```text
忘记密码怎么办？
```

扩展为：

```text
忘记密码如何找回？
如何重置密码？
密码重置流程是什么？
```

### 作用

用户问题不一定天然适合检索。

Query 预处理可以明显提升召回率。

---

## 12. Retriever 检索器组件

### 功能

负责根据用户问题从知识库中找候选 chunk。

它是 RAG 运行时的核心组件。

### 输入

```json
{
  "query": "如何创建 Agent？",
  "knowledgeBaseIds": [1, 2],
  "topK": 10,
  "similarityThreshold": 0.6
}
```

### 输出

```json
[
  {
    "chunkId": 101,
    "content": "用户可以在控制台点击创建 Agent...",
    "score": 0.82,
    "documentName": "Hify 使用手册.md",
    "pageNumber": 5
  }
]
```

### 检索器职责

- 调用 embedding 生成 query 向量
- 查询向量数据库
- 执行 metadata 过滤
- 执行 topK 限制
- 执行相似度阈值过滤
- 返回候选文档片段

---

## 13. Metadata 过滤组件

### 功能

根据文档元数据缩小检索范围。

例如：

```text
department = HR
document_type = policy
language = zh
created_at > 2026-01-01
```

### 使用场景

用户问：

```text
研发部门的报销规则是什么？
```

可以先过滤：

```text
department = 研发
category = 报销制度
```

再检索。

### 作用

可以提高检索准确率，减少无关文档干扰。

---

## 14. Reranker 重排序组件

### 功能

对初步检索出的候选 chunk 重新排序。

向量检索通常是粗召回，rerank 是精排。

### 示例流程

```text
向量检索 top 30
  ↓
Reranker 重新打分
  ↓
取 top 5
  ↓
交给 LLM
```

### Reranker 输入

```text
query + chunk
```

### Reranker 输出

```text
相关性分数
```

### 为什么需要 Reranker？

向量检索找的是“语义相近”，但不一定是“最能回答问题”。

Reranker 会逐条判断：

```text
这个 chunk 是否真的能回答这个问题？
```

### 作用

Reranker 通常能显著提高最终答案质量，但会增加延迟和成本。

---

## 15. 上下文压缩组件

### 功能

当检索结果太多或太长时，对上下文进行压缩。

原因是：

- LLM 上下文窗口有限
- Prompt 太长成本高
- 无关内容会干扰生成

### 常见方式

- 直接截断：按分数取前几条
- 摘要压缩：把多个 chunk 摘成短上下文
- 句子级筛选：只保留 chunk 中和问题最相关的句子
- 去重：删除重复或高度相似的片段

### 作用

控制 Prompt 长度，提高回答稳定性。

---

## 16. Prompt 组装组件

### 功能

把用户问题、检索结果、系统指令组装成最终 Prompt。

### 典型 Prompt

```text
你是一个知识库问答助手。
请严格根据给定资料回答用户问题。
如果资料中没有答案，请回答“知识库中没有找到相关信息”，不要编造。

资料：
[1] 用户可以在控制台点击“创建 Agent”按钮...
来源：Hify 使用手册.md，第 3 节

[2] 创建 Agent 时需要选择模型配置...
来源：Hify 管理员手册.md，第 5 页

用户问题：
如何创建 Agent？

请给出答案，并列出引用来源。
```

### 作用

Prompt 直接影响：

- 是否基于资料回答
- 是否减少幻觉
- 是否返回引用
- 是否保持格式稳定
- 是否拒绝回答无依据内容

---

## 17. LLM 生成组件

### 功能

调用大模型生成最终答案。

可调用：

- OpenAI
- Claude
- Gemini
- Ollama
- 其他兼容 OpenAI API 的模型

### 输入

```text
system prompt + retrieved context + user query
```

### 输出

```text
自然语言答案
```

### 组件职责

- 选择模型
- 设置 temperature
- 设置 max tokens
- 设置超时
- 处理流式输出
- 处理模型调用异常
- 处理限流和重试

### 作用

LLM 不负责查资料，而是负责基于资料进行表达、总结和推理。

---

## 18. 引用来源组件

### 功能

把答案和来源文档关联起来。

常见引用信息：

```text
文档名称
页码
章节标题
chunk id
相似度分数
原文片段
```

### 示例返回

```json
{
  "answer": "可以在控制台点击“创建 Agent”按钮创建 Agent。",
  "citations": [
    {
      "documentName": "Hify 使用手册.md",

  ]
}
```

### 作用

引用来源让 RAG 答案可追溯、可验证。

企业内部系统通常非常需要这个能力。

## 19. 对话上下文组件

### 功能

在多轮对话中保存历史消息。

例如：

```text
用户：怎么创建 Agent？
助手：...
用户：那怎么绑定知识库？
```

第二个问题里的“那”依赖上一轮上下文。

### 组件职责

- 保存会话历史
- 控制历史消息长度
- 生成 standalone question
- 避免把过长历史全部塞给 LLM
- 区分“用于检索的上下文”和“用于回答的上下文”

### 作用

让 RAG 支持多轮连续问答，而不是只能回答单轮问题。

## 20. 权限控制组件

### 功能

控制用户能检索哪些知识。

即使 Hify 当前不做复杂权限体系，完整 RAG 系统里这个组件也很重要。

### 示例

```text
普通员工：只能查员工手册
HR：可以查薪酬制度
研发：可以查技术文档
管理员：可以查全部知识库
```

### 作用

防止 RAG 泄露用户无权访问的文档。

权限控制应该在检索前完成，而不是生成后再过滤。

避免上传接口阻塞太久，提高系统稳定性。

## 十五、在 Hify 项目里的 RAG 落地方式

结合 Hify 当前规划，RAG 模块可以对应到 `hify-knowledge`。

核心表可以是：

```text
knowledge_base
document
document_chunk
```

基础流程：

```text
1. 创建知识库
2. 上传文档
3. 解析文档
4. 切分 chunk
5. 调用 embedding 模型生成向量
6. 存入 pgvector
7. Agent 绑定知识库
8. 对话时先检索知识库
9. 把检索结果放进 Prompt
10. LLM 基于检索结果回答
11. 返回答案和引用来源
```

最小可用版本可以先做：

```text
- 支持 txt / md 文档上传
- 固定 chunk size
- 使用一个 embedding provider
- pgvector 相似度检索
- topK 固定为 5
- 回答时附带文档名和 chunk 内容引用
```

后续再增强：

```text
- PDF / Word 解析
- 混合检索
- rerank
- metadata 过滤
- 多知识库绑定
- 文档增量更新
- 引用高亮
```

## 十六、总结

RAG 的本质是：

> 让大模型在回答前先查资料，再基于查到的资料生成答案。

它特别适合：

- 企业知识库问答
- 产品文档问答
- 客服机器人
- 法律 / 合同问答
- 代码库问答
- 内部制度查询
- AI Agent 的知识增强

完整 RAG 系统不是只有“向量数据库 + 大模型”，而是一整条链路：

```text
文档进来 -> 解析清洗 -> 切块向量化 -> 存储索引
用户提问 -> 检索召回 -> 排序筛选 -> 组装上下文
大模型回答 -> 返回引用 -> 记录评估
```

其中最核心的 5 个组件是：

```text
1. 文档解析与切块
2. Embedding 向量化
3. 向量数据库
4. Retriever 检索器
5. Prompt + LLM 生成
```

一句话概括：

> RAG 不是让模型“记住所有知识”，而是让模型“会查资料并基于资料回答”。
