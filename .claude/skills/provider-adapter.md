# Provider Adapter 开发流程 Skill

适用于 Hify Provider 模块中对接不同模型供应商 API，尤其是连通性测试、模型列表同步、健康检查等供应商差异明显的能力。

核心约定：不同供应商 API 适配使用策略模式。新增供应商流程固定为：分析 API -> 实现 Adapter -> 注册到 Factory -> 验证。

## 0. 启动前检查

### 要做什么
- 阅读 Provider 模块现有连通性测试、模型同步、健康检查相关代码。
- 确认当前是否已有 Adapter 接口、Factory、ProviderType 枚举或等价注册机制。
- 确认新增供应商是否属于已有 Provider 类型，还是需要新增类型。
- 确认是否涉及外部调用超时、认证方式、请求头、baseUrl、模型列表接口。

### 产出物
- 现有适配结构说明。
- 新供应商接入范围说明。
- 待确认问题清单。

### 验证方式
- 能明确回答：供应商类型是什么、认证方式是什么、连通性测试调用哪个接口、成功和失败如何判断。

### 关键决策点
- 新供应商是否纳入当前 Provider 模块范围：等待用户确认。
- 供应商类型命名、默认 baseUrl、是否支持模型同步：等待用户确认。
- 如果需要新增依赖或改变现有接口契约：等待用户确认。

## 1. 分析供应商 API

### 要做什么
- 阅读供应商官方 API 文档或用户提供的接口说明。
- 明确认证方式：Bearer Token、API Key Header、自定义 Header、Basic Auth 等。
- 明确连通性测试接口：优先选择轻量、只读、低成本接口。
- 明确请求方法、URL、Header、Query、Body、超时时间。
- 明确成功判断标准和常见失败类型。

### 产出物
- API 分析结果：认证方式、测试接口、模型同步接口、错误响应格式。
- 字段映射说明：Hify 内部字段如何映射到供应商请求。
- 失败场景表：认证失败、限流、网络超时、服务端错误、响应格式异常。

### 验证方式
- 用 curl 或最小请求验证供应商 API 行为。
- 能拿到真实成功响应或明确的失败响应。
- 能判断哪些异常可重试，哪些异常不可重试。

### 关键决策点
- 连通性测试选用哪个 API：等待用户确认。
- 是否使用模型列表接口作为连通性测试：等待用户确认。
- 是否需要兼容供应商私有部署 baseUrl：等待用户确认。

### 注意事项
- 不要选择会产生费用、写入数据或触发模型推理的接口做默认连通性测试，除非用户确认。
- 外部调用必须有超时设置；连通性测试按 Hify 规范控制在 10s 内。
- 认证失败不要重试；限流可以退避；网络抖动才考虑重试。
- 不要把 API Key 输出到日志、异常消息或前端响应中。

## 2. 设计 Adapter 契约

### 要做什么
- 使用统一 Adapter 接口屏蔽供应商差异。
- Adapter 只处理供应商协议差异：请求构造、认证头、响应解析、错误转换。
- 业务编排留在 Service，Factory 只负责根据供应商类型选择 Adapter。
- Adapter 接口保持稳定，避免因某个供应商的特殊字段污染通用契约。

### 产出物
- Provider Adapter 接口或现有接口的最小扩展。
- 通用请求 / 响应对象。
- 供应商错误到 Hify 错误码的映射规则。

### 验证方式
- 现有供应商 Adapter 不需要大改即可继续编译通过。
- Service 层不需要知道供应商具体 API 细节。
- 新增供应商只需要新增 Adapter 和注册逻辑。

### 关键决策点
- Adapter 接口是否需要新增方法，例如 `testConnection`、`syncModels`、`healthCheck`：等待用户确认。
- 某个供应商的特殊能力是否进入通用接口：等待用户确认。

### 注意事项
- 不要把 Factory 写成复杂业务中心；它只做选择策略。
- 不要在 Service 中用大量 `if providerType == ...` 拼供应商逻辑，应下沉到 Adapter。
- 不要为了一个供应商过度抽象通用模型，先保持最小接口。

## 3. 实现 Adapter

### 要做什么
- 为每个供应商实现独立 Adapter。
- Adapter 内部完成请求 URL 拼接、Header 构造、Body 构造、响应解析。
- 对外返回统一结果，不泄露供应商原始响应结构给 Service。
- 外部调用读取配置项，不硬编码超时、默认 baseUrl 等可变配置。

### 产出物
- 新供应商 Adapter 实现类。
- 必要的配置项更新。
- 供应商响应 DTO 或内部解析结构。
- 错误处理和异常转换逻辑。

### 验证方式
- Maven 编译通过。
- 使用 mock 配置或真实测试配置调用 Adapter 的核心方法。
- 成功响应能转换成统一结果。
- 失败响应能转换成模块 ErrorCode，而不是抛出裸异常或硬编码错误消息。

### 注意事项
- 不要硬编码 API Key、baseUrl、模型名或超时时间。
- 不要在 Adapter 里写 Provider 数据库 CRUD。
- 不要把供应商响应对象直接作为 Controller 响应返回。
- 注意不同供应商错误响应字段不同，解析失败时也要给出稳定的业务错误。
- 如果供应商支持自定义 baseUrl，URL 拼接要避免双斜杠、漏路径、覆盖路径。

## 4. 注册到 Factory

### 要做什么
- 将新 Adapter 注册到 Factory 或策略 Map。
- Factory 根据 Provider 类型返回对应 Adapter。
- 未支持的 Provider 类型返回明确错误，不要返回 null。
- 如果使用 Spring 注入，优先通过 Bean 集合自动组装策略 Map，减少手动分支。

### 产出物
- Factory 注册逻辑。
- Provider 类型到 Adapter 的映射。
- 未支持类型的错误处理。

### 验证方式
- Maven 编译通过。
- 新 Provider 类型能获取到正确 Adapter。
- 已有 Provider 类型仍能获取原 Adapter。
- 未注册类型能得到可预期错误。

### 关键决策点
- 使用手动注册、枚举匹配还是 Spring Bean 自动注册：等待用户确认。

### 注意事项
- 不要在 Factory 中调用外部 API。
- 不要让 Factory 返回 null 后交给调用方猜测错误原因。
- 不要因为新增供应商破坏已有 Provider 类型名称或接口契约。

## 5. 接入 Service 流程

### 要做什么
- Service 根据 Provider 配置读取 Provider 类型、API Key、baseUrl 等信息。
- Service 调用 Factory 获取 Adapter，再调用统一方法执行连通性测试或模型同步。
- Service 负责业务校验、持久化、健康状态更新；Adapter 负责供应商协议。
- 错误统一使用 ErrorCode 枚举。

### 产出物
- Service 层调用策略模式后的流程。
- 连通性测试结果保存或返回逻辑。
- 模型同步结果处理逻辑。
- 健康检查状态更新逻辑。

### 验证方式
- 现有连通性测试 API curl 仍能工作。
- 新供应商走新 Adapter，不影响旧供应商。
- 认证失败、超时、限流、未知供应商类型都有明确响应。

### 注意事项
- 不要把 Adapter 选择逻辑散落在多个 Service 方法里。
- 不要在 Controller 直接调用 Adapter。
- 不要绕过统一 Result 和 ErrorCode。

## 6. 后端验证

### 要做什么
- 编译整个后端或 Provider 相关模块。
- 启动服务，用 curl 验证新供应商创建、连通性测试、模型同步、健康状态。
- 同时回归至少一个已有供应商，确认重构没有破坏旧逻辑。

### 产出物
- 编译结果。
- curl 验证命令和响应摘要。
- 回归验证结论。

### 验证方式
- Maven 编译通过。
- `POST /api/v1/providers/{id}/test-connection` 对新供应商返回预期结果。
- 错误 API Key 返回认证失败类错误。
- 不可达 baseUrl 返回超时或网络失败类错误。
- 已有供应商连通性测试仍通过或保持原有行为。

### 注意事项
- curl 验证不要只测成功路径，至少覆盖认证失败和超时 / 不可达。
- 如果真实供应商 API 不可访问，要说明使用了什么替代验证方式。

## 7. 前端验证

### 要做什么
- 如新增 Provider 类型需要前端展示，更新类型枚举、表单选项、默认 baseUrl 或提示文案。
- 确认页面调用的仍是统一 Provider API，不直接感知 Adapter。
- 在浏览器中创建该供应商并执行连通性测试。

### 产出物
- 前端 Provider 类型选项更新。
- 表单字段展示和校验更新。
- 浏览器验收结果。

### 验证方式
- 前端类型检查或构建通过。
- 浏览器中能选择新供应商。
- 填写配置后能发起真实连通性测试。
- 网络请求和页面提示符合后端响应。

### 注意事项
- 不要在前端硬编码供应商协议细节，前端只负责收集配置和展示结果。
- 如果 API Key 回显，应使用脱敏值或空值，不要显示明文。

## 8. 交付总结

### 要做什么
- 总结新增供应商 API 分析结论、Adapter 实现、Factory 注册、验证结果。
- 明确哪些能力已支持：连通性测试、模型同步、健康检查。
- 明确哪些未支持或需要后续确认。

### 产出物
- 变更摘要。
- 验证摘要。
- 风险和后续事项。

### 验证方式
- 用户能根据摘要判断是否可以合并或继续扩展下一个供应商。

## 固定新增供应商流程

1. 分析 API：认证方式、测试接口、响应格式、错误格式、超时和重试策略。
2. 实现 Adapter：封装请求构造、响应解析、错误转换。
3. 注册到 Factory：Provider 类型映射到 Adapter，未支持类型明确报错。
4. 验证：编译、curl、浏览器、旧供应商回归。

## 常见坑位清单

- Service 里写大量供应商 `if/else`，导致每新增一个供应商都要改业务流程。
- Factory 承担业务逻辑，变成第二个 Service。
- Adapter 返回供应商原始响应，导致 Controller 或前端被供应商协议污染。
- 连通性测试接口选择了模型推理接口，可能产生费用或延迟过高。
- 外部调用没有 10s 超时，导致请求线程被拖住。
- API Key 出现在日志、异常消息、curl 输出或页面回显中。
- 只验证新供应商，忘记回归已有 OpenAI、Claude、Gemini、Ollama 等供应商。
- 新增 Provider 类型后只改后端，前端下拉选项没有同步。
- baseUrl 拼接不严谨，出现双斜杠、路径重复或路径丢失。
- 认证失败被当成网络失败重试，浪费时间并掩盖真实错误。
