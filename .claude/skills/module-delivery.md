# Hify 模块交付流程 Skill

适用于 Hify 项目中按模块交付新功能，例如 Provider、Agent、Chat、MCP、Workflow、Knowledge 等模块。

目标：用最小可行实现完成一个模块闭环，每一步都有明确产出物和验证方式；涉及架构、数据模型、接口契约、边界行为时必须等待用户确认。

## 0. 启动前检查

### 要做什么
- 阅读 `CLAUDE.md`，确认当前模块的架构边界、接口规范、错误码范围、线程池要求、缓存策略。
- 查看当前 git 状态，识别已有未提交文件，避免覆盖用户工作。
- 确认模块名称、功能范围、是否需要前端页面、是否需要外部调用。

### 产出物
- 模块范围说明：本次做什么、不做什么。
- 影响文件清单初稿。
- 待确认问题清单。

### 验证方式
- 能明确回答：模块属于哪个业务域、接口路径是什么、错误码段是什么、是否需要数据库变更、是否需要前端对接。

### 关键决策点
- 模块范围和边界：等待用户确认。
- 是否引入新依赖、缓存、异步任务、外部服务调用：等待用户确认。

## 1. 咨询模式梳理方案

### 要做什么
- 先不要写代码，先梳理业务目标、核心实体、关键流程、边界问题。
- 给出 2-3 个可选方案，只比较必要差异，不过度设计。
- 明确本模块的 MVP 范围，避免把后续阶段能力一次性塞进来。

### 产出物
- 业务流程草图或步骤说明。
- 核心数据模型候选方案。
- API 草案：路径、方法、请求体、响应体、错误场景。
- 边界问题列表：空值、重复、删除、状态流转、外部调用失败、超时、重试等。

### 验证方式
- 用户能基于方案拍板。
- 后续代码实现不需要再临时发明核心规则。

### 关键决策点
- 供应商 / 模型 / Agent / 工具等核心概念怎么抽象：等待用户确认。
- 数据库表结构和字段含义：等待用户确认。
- 接口契约和错误行为：等待用户确认。

## 2. 数据模型设计与 schema 更新

### 要做什么
- 根据确认后的模型更新数据库 schema。
- 遵守数据库规范：表名和字段小写下划线、主键 `id`、时间字段 `created_at` / `updated_at`、逻辑删除 `deleted`、不建数据库级外键。
- 先完成表结构，再写后端代码，避免 Entity 和数据库反复对不齐。

### 产出物
- `schema.sql` 或对应迁移 SQL 更新。
- 表字段说明和索引设计。
- 必要的初始化数据或枚举取值说明。

### 验证方式
- SQL 能在 MySQL 8.x 执行通过。
- 表结构与后续 Entity 字段一一对应。
- 索引满足主要查询路径。

### 关键决策点
- 字段是否冗余存储、状态枚举取值、唯一约束、软删除策略：等待用户确认。

### 注意事项
- 不要只改 Entity 不改 schema，最终会在运行时或 curl 验证时暴露字段不匹配。
- 不要建立数据库外键，Hify 规范要求外键在应用层维护。
- 大表分页不要默认依赖 `SELECT COUNT(*)`，尤其是聊天消息类增长快的表。

## 3. 后端 Entity + Mapper

### 要做什么
- 在对应模块下创建或更新 `entity/`、`mapper/`。
- Entity 字段严格匹配 schema。
- Mapper 保持简单，优先使用 MyBatis-Plus 基础能力。

### 产出物
- Entity 类。
- Mapper 接口。
- 必要的 Mapper XML 或自定义查询。

### 验证方式
- 执行 Maven 编译，确认类型、注解、包路径无误。
- 如有自定义 SQL，启动后执行一次最小查询验证。

### 注意事项
- 不要跨模块直接引用其他模块 Mapper 或 Entity，跨模块调用走 Service 接口。
- 不要在 Mapper 层写业务逻辑。

## 4. DTO 与错误码

### 要做什么
- 按接口契约创建请求 DTO 和响应 DTO。
- DTO 只表达接口输入输出，不直接暴露 Entity。
- 模块错误必须使用 `ErrorCode` 枚举，禁止硬编码错误码和错误信息。
- 参数校验放在 Controller 入参层，业务校验放在 Service 层。

### 产出物
- Create / Update / Query / Response 等 DTO。
- 对应模块错误码枚举项。
- 必要的参数校验注解。

### 验证方式
- Maven 编译通过。
- DTO 字段能覆盖前端页面和 curl 验证所需数据。
- 错误响应仍符合统一 `Result<T>` 结构。

### 关键决策点
- 哪些字段对外暴露、哪些字段只内部使用：等待用户确认。

### 注意事项
- 不要把敏感字段原样返回给前端，例如 API Key 应脱敏或不返回明文。
- 字符串空值按规范返回 `""`，列表空值返回 `[]`，不要返回 `null`。

## 5. Service 实现业务闭环

### 要做什么
- 先定义 Service 接口，再实现 `service/impl/`。
- 按最小闭环实现核心能力：CRUD、状态变更、连通性测试、模型同步、健康检查等。
- 外部调用必须配置超时；LLM 调用使用 `@Qualifier("llmExecutor")` 注入线程池。
- 业务异常统一使用 ErrorCode。

### 产出物
- Service 接口。
- Service 实现类。
- 必要的配置项，写入 `application.yml`，不要硬编码。
- 外部调用客户端或适配逻辑。

### 验证方式
- Maven 编译通过。
- 单独验证核心 Service 路径：新增、查询、更新、删除、异常场景。
- 外部调用类功能用可控参数验证超时和失败返回。

### 关键决策点
- 外部服务的超时、重试、失败降级、健康状态口径：等待用户确认。
- 模型同步是手动触发、定时触发还是创建后自动触发：等待用户确认。

### 注意事项
- 禁止在业务代码中 `new Thread()` 或使用默认线程池。
- 不要把连通性测试做成无超时阻塞调用。
- 不要为了统一供应商差异过度抽象；先用简单直接的分支或适配实现。
- 认证失败不要重试，限流应退避，网络抖动才考虑重试。

## 6. Controller 暴露 REST API

### 要做什么
- Controller 只做参数校验和调用 Service，不写业务逻辑。
- 路径遵守 `/api/v1/{资源复数名}`。
- CRUD 使用 RESTful 方法，非 CRUD 动作用动词子路径，例如 `POST /api/v1/providers/{id}/test-connection`。
- 所有接口返回 `Result<T>`。

### 产出物
- Controller 类。
- 完整 API 路由。
- curl 验证命令清单。

### 验证方式
- Maven 编译通过。
- 启动后用 curl 验证：创建、列表、详情、更新、删除、关键动作接口、错误场景。
- 确认响应结构统一：`code`、`message`、`data`。

### 注意事项
- 不要在 Controller 拼业务规则。
- 不要破坏已有接口契约。
- 分页参数从 1 开始，`pageSize` 默认 20，最大 100。

## 7. 每步编译和最小验证

### 要做什么
- 每完成一个垂直层级就验证，不要等所有代码写完再一起排错。
- 推荐顺序：schema -> Entity/Mapper -> DTO/ErrorCode -> Service -> Controller -> curl。

### 产出物
- 编译结果。
- curl 命令和响应样例。
- 发现的问题和修复记录。

### 验证方式
- Maven 编译通过。
- 后端服务能启动。
- 核心 API curl 返回符合预期。

### 注意事项
- 分层开发时，小步验证比一次性写完整模块更稳。
- curl 验证不仅测成功路径，也要测参数错误、资源不存在、外部调用失败。

## 8. 前端 API 对接

### 要做什么
- 在 `hify-web/src/api/` 按模块创建或更新 API 文件。
- 在 `hify-web/src/types/` 创建或更新 TypeScript 类型。
- 把页面里的 mock 数据源替换成真实 API。
- 保持页面结构简单，优先完成真实数据闭环。

### 产出物
- 模块 API 文件。
- TypeScript 请求 / 响应类型。
- 页面数据加载、提交、更新、删除、动作按钮对接真实接口。

### 验证方式
- 前端类型检查或构建通过。
- 浏览器打开页面，能看到后端真实数据。
- 页面操作后刷新仍能看到持久化结果。

### 关键决策点
- 页面交互细节、字段展示、敏感信息展示方式：等待用户确认。

### 注意事项
- mock 替换要彻底，避免页面看起来成功但实际没调后端。
- API 响应有统一 `Result<T>` 包装，前端取数据时不要漏掉 `data` 层级。
- 注意列表字段空值要按 `[]` 处理，避免组件报错。

## 9. 浏览器全流程验收

### 要做什么
- 启动后端和前端开发服务。
- 在浏览器完成真实用户路径，不只依赖编译和 curl。
- 覆盖黄金路径和关键边界路径。

### 产出物
- 验收路径清单。
- 浏览器验证结论。
- 如有问题，记录复现步骤和修复点。

### 验证方式
- 后端 curl 验证通过。
- 浏览器页面完成：列表加载、创建、详情 / 编辑、删除、关键动作。
- 刷新页面后数据状态正确。
- 控制台无明显错误，网络请求状态码和响应符合预期。

### 注意事项
- 前端改动必须浏览器验证；类型检查和测试不能替代真实 UI 验收。
- 如果当前环境无法打开浏览器或启动服务，要明确说明未完成 UI 验收，不要声称已验证。

## 10. 交付总结

### 要做什么
- 简短总结改了什么、验证了什么、还有什么未覆盖。
- 不创建额外文档，除非用户要求。
- 不主动提交 git，除非用户明确要求。

### 产出物
- 变更摘要。
- 验证摘要。
- 风险或后续事项。

### 验证方式
- `git status` 能清楚展示本次改动范围。
- 用户能直接基于摘要 review 或要求提交。

## 常见坑位清单

- schema、Entity、DTO 三者字段不一致，导致编译通过但运行失败。
- Controller 写入业务逻辑，后续难以复用和测试。
- 错误码或错误信息硬编码，违反 Hify 规范。
- 外部调用没有超时，连通性测试会拖垮请求线程。
- 使用默认线程池或 `new Thread()`，违反线程池规范。
- 前端仍然读取 mock 数据，导致“看起来完成”但没有真实闭环。
- 前端忘记处理统一响应 `Result<T>` 的 `data` 包装。
- API Key 等敏感字段直接回显到页面。
- 只测成功路径，没测资源不存在、参数错误、认证失败、外部服务超时。
- 只跑编译不做浏览器验收，容易漏掉页面交互和网络层问题。

## 推荐执行节奏

1. 咨询梳理，等待用户确认核心方案。
2. 更新 schema，执行 SQL 验证。
3. 写 Entity + Mapper，编译验证。
4. 写 DTO + ErrorCode，编译验证。
5. 写 Service，实现核心业务，编译和最小验证。
6. 写 Controller，curl 验证 API。
7. 写前端 API 和类型，替换 mock。
8. 浏览器完整验收。
9. 汇总变更和验证结果。
